# T-011 Contracts Reference (English)

This document explains the T-011 implementation line by line. Blank lines are
used only for readability and are not discussed separately. The implementation
contains four source concepts: shared types, clone-ready collection contracts,
the factory, and Foundry tests.

## 1. `CollectionTypes.sol`

- Lines 1-2 identify the MIT license and require exactly Solidity `0.8.24`.
- Lines 4-7 define `CollectionStandard`, an enum with two valid values:
  `ERC721` and `ERC1155`. Solidity stores enum values as small integers; the
  enum makes the factory API self-describing instead of passing magic numbers.
- Lines 9-16 define `CollectionMetadata`. It groups the collection name,
  symbol, primary metadata URI, description, image URI, and external URL into a
  single ABI tuple. The strings are stored on each initialized clone and in the
  factory registry.
- Lines 18-24 define `ICollectionInitializable`. A clone cannot use a normal
  constructor, so the factory calls this external `initialize` function after
  deployment. `calldata` avoids copying the metadata tuple before the call;
  `uint96` matches OpenZeppelin ERC-2981 royalty storage.

## 2. `CreatorCollection.sol`

### Imports and `CollectionBase`

- Lines 1-2 set the license and compiler version.
- Lines 4-7 import OpenZeppelin ERC-721, ERC-1155, ERC-2981, and the shared
  metadata/initializer definitions.
- Line 9 declares `CollectionBase` as abstract. It combines royalty support and
  common creator metadata, while concrete token standards supply their own
  token-standard behavior.
- Lines 10-12 declare custom errors for repeated initialization, unauthorized
  owner-only actions, and a zero creator address. Custom errors use less gas
  than revert strings.
- Lines 14-21 declare public state. `owner` is the creator address, `initialized`
  prevents initializer takeover, and the six public strings expose collection
  metadata through autogenerated getters.
- Lines 23-26 define `onlyOwner`. Calls from any address other than the stored
  creator revert with `Unauthorized`; `_` marks the protected function body.
- Lines 28-33 declare `_initializeBase`, the shared internal initializer called
  by both standards.
- Line 34 rejects a second initialization. This is essential for minimal
  proxies because clone constructors do not run.
- Line 35 rejects the zero address as creator.
- Line 36 marks the clone initialized before writing other state. This follows
  the checks-effects pattern and prevents reentrant or repeated setup.
- Line 37 assigns creator ownership.
- Lines 38-43 copy every metadata field from calldata into storage.
- Line 44 calls OpenZeppelin `_setDefaultRoyalty`, configuring ERC-2981 for all
  token IDs. The factory already enforces the 0-1000 bps policy.
- Lines 47-49 forward ERC-165 interface checks to ERC-2981. Concrete contracts
  combine this implementation with their token-standard interface support.

### `CreatorERC721`

- Line 52 declares the ERC-721 collection implementation.
- Lines 53-55 run the base ERC-721 constructor with empty placeholder identity
  and mark the standalone implementation initialized. That lock prevents a
  user from initializing the implementation contract itself; clones start with
  fresh storage and remain uninitialized.
- Lines 57-64 expose the required initializer and delegate all common setup to
  `_initializeBase`.
- Lines 66-68 override ERC-721 `name()` to return the initialized collection
  name instead of the constructor placeholder.
- Lines 70-72 do the same for `symbol()`.
- Lines 74-76 resolve multiple inheritance and preserve both ERC-721 and
  ERC-2981 interface detection.

### `CreatorERC1155`

- Line 79 declares the ERC-1155 collection implementation.
- Lines 80-82 use an empty constructor URI and lock direct initialization, for
  the same implementation-versus-clone reason as ERC-721.
- Lines 84-90 expose the shared initializer.
- Line 91 sets OpenZeppelin's ERC-1155 base URI during initialization.
- Lines 94-96 return the stored collection URI for every token ID. T-013 may
  later add token-specific URI and freeze behavior.
- Lines 98-100 resolve ERC-1155 plus ERC-2981 interface support.

## 3. `CreatorCollectionFactory.sol`

- Lines 1-6 set compiler metadata and import Ownable, deterministic Clones,
  and the shared types.
- Line 8 declares the factory as `Ownable`; T-011 uses an owner for approval
  administration, while T-015 is responsible for stronger governance.
- Line 9 enables calling `cloneDeterministic` directly on implementation
  addresses.
- Lines 11-17 define validation errors. `ImplementationStandardMismatch` is
  reserved for a future runtime interface check; the current approval mapping
  is the standard binding.
- Lines 19-27 define `CollectionRecord`, the complete registry entry for a
  deployment.
- Lines 29-32 declare storage: approved implementations per standard, salts
  used by each creator and standard, private collection records, and the nonce
  used for generated salts.
- Lines 34-49 define events. `ImplementationApprovalUpdated` audits allowlist
  changes. `CollectionDeployed` includes indexed collection/creator/
  implementation addresses plus standard, all metadata, royalty information,
  and the effective salt for indexers.
- Line 51 initializes the OpenZeppelin owner.
- Lines 53-57 implement owner-only approval/revocation. Zero implementations
  are rejected, the mapping is updated, and an audit event is emitted.
- Lines 59-66 declare `deployCollection`. The caller selects the standard and
  approved implementation, supplies metadata, royalty settings, and an
  optional salt; the function returns the clone address.
- Line 67 rejects zero implementation and royalty recipient addresses.
- Line 68 requires a non-empty name and metadata URI.
- Line 69 additionally requires an ERC-721 symbol.
- Line 70 enforces the maximum royalty of 1,000 basis points (10%); zero is
  valid.
- Line 71 rejects implementations absent from the selected standard's allowlist.
- Line 72 rejects enum values other than ERC-721 or ERC-1155.
- Line 74 starts with the caller-provided salt.
- Lines 75-76 replace an all-zero salt with `keccak256(msg.sender, nonce)` and
  increment the nonce. This permits repeated deployments without caller salt.
- Lines 77-80 track non-zero salts per creator and standard and reject reuse.
- Line 82 deploys an ERC-1167 deterministic clone.
- Line 83 calls the clone initializer, assigning `msg.sender` as creator.
- Line 84 stores the complete registry record.
- Line 85 emits the canonical deployment event through a helper to avoid a
  Solidity stack-too-deep error.
- Lines 88-101 implement `_storeCollection`, isolating the large struct write.
- Lines 103-121 implement `_emitCollectionDeployed`. It reads the stored record
  and emits every field after deployment succeeds.
- Lines 123-125 return a collection record for off-chain readers.
- Lines 127-130 predict a deterministic address. For a zero salt it predicts
  the next nonce-derived deployment for the supplied creator; otherwise it uses
  the caller's salt. The `standard` parameter is accepted for API symmetry but
  address derivation itself depends on implementation, salt, and factory.

## 4. `CreatorCollectionFactory.t.sol`

- Lines 1-7 set compiler metadata and import Forge Std, the factory, concrete
  implementations, and shared types.
- Lines 9-15 declare test fixtures: factory, approved implementations, creator,
  royalty recipient, and representative metadata.
- Lines 17-23 deploy the factory and implementations, then approve each under
  its matching standard.
- Lines 25-46 test ERC-721 deployment, deterministic prediction, the complete
  deployment event, creator ownership, name, royalty calculation, and registry
  persistence.
- Lines 48-53 test ERC-1155 deployment, creator ownership, and URI storage.
- Lines 55-61 verify unapproved implementations and royalty values above 10%
  revert.
- Lines 63-69 verify a creator cannot reuse a non-zero salt for the same
  standard.
- Lines 71-75 verify only the factory owner can change implementation approval.

## Runtime flow and boundaries

1. The owner approves a known implementation for a standard.
2. A creator calls `deployCollection`.
3. The factory validates inputs, derives a salt, clones the implementation,
   initializes the clone, stores the record, and emits one event.
4. Indexers can use the event as the deployment source of truth and use the
   registry/getters for confirmation.

Minting, metadata updates, freezing, supply tracking, marketplace settlement,
and multisig governance are intentionally outside T-011 and belong to later
tasks T-012 through T-015.
